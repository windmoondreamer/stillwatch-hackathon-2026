# StillWatch 휴대기기 음성 대기 검증

2026-10-09, USB로 연결된 삼성 SM-X930 / Android 16(API 36) 실기기에서 확인했습니다. 검증 앱의 targetSdk는 35입니다. 기존 앱과 다른 패키지(`com.stillwatch.voiceprobe`)를 사용했습니다.

**앱이 화면에 보일 때 음성 대기 서비스를 먼저 시작하면, 홈 화면 및 화면이 꺼진 잠금 상태에서도 한국어 질문을 재생하고 마이크 입력을 받을 수 있었습니다.** 사용자가 강제 종료하거나 실행 중 앱을 중지하면 이 대기는 중단됐습니다. 앱 화면을 자동으로 띄우는 기능은 구현하지 않았습니다.

## 실기기 결과

| 조건 | 질문 재생 로그 | 마이크 입력 | 사용자 청취 확인 |
|---|---|---|---|
| 앱 화면 열림 | 한국어 TTS 완료 | 29,696 샘플, 시스템 음소거 아님 | 별도 확인 없음 |
| 홈 화면으로 전환 | 한국어 TTS 완료 | 29,696 샘플, 시스템 음소거 아님 | 들림 |
| 화면 꺼짐 + 잠금 | 한국어 TTS 완료 | 27,648 샘플, 시스템 음소거 아님 | 최종 재시험에서 들림 |
| 실행 중 앱 중지 | 예약 질문 실행 안 됨 | 실행 안 됨 | 해당 없음 |
| 설정의 강제 종료에 해당하는 명령 | 예약 질문 실행 안 됨 | 실행 안 됨 | 해당 없음 |

중지 시험은 각각 질문을 10초 뒤로 예약한 뒤 앱을 중지하고 18초간 관찰했습니다. 두 경우 앱 프로세스도 없었습니다. ‘실행 중 앱 중지’는 공식 시험 명령 `adb shell cmd activity stop-app PACKAGE`로 검사했습니다. 이 동작은 최근 앱 목록에서 카드를 밀어 없애는 동작과 구분해야 합니다. 최근 앱 카드 제거는 이번에 검사하지 않았습니다. [Android의 사용자 중지 동작](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)

잠금 상태의 앞선 시험은 로그에 재생 완료가 있어도 사용자가 소리를 듣지 못했다고 보고했습니다. 따라서 그 시험을 실제 청취 성공으로 집계하지 않았습니다. 마지막 재시험에서 사용자가 소리가 나온다고 확인했습니다. 그때 `interactive=false`, `locked=true`, `mediaVolume=15/15`, `mediaMuted=false`였으며 질문과 마이크 시험 내내 잠금 상태가 유지됐습니다. 음량은 사용자가 조절했고 시험 도구는 음량을 변경하지 않았습니다. 어느 설정 변화가 앞선 미청취의 원인이었는지는 확정하지 못했습니다.

`AudioManager.getDevices()`로 기록한 장치 종류는 사용 가능한 출력 장치 목록입니다. 실제 선택된 출력 경로를 증명하는 값은 아닙니다. 스피커로 들렸다는 결론은 사용자 확인을 함께 근거로 합니다.

## 검증 앱의 동작

앱을 열어 마이크·알림 권한을 받은 뒤 `microphone|mediaPlayback` foreground service를 시작합니다. 상태 알림을 계속 표시합니다. 이 시험에서는 사용자 승인 아래 ADB로 두 권한을 부여했으므로, 일반 설치 시 권한 요청 화면의 사용성은 별도로 확인해야 합니다.

서비스를 시작한 뒤 10초가 지나면 짧은 삑 소리와 “괜찮으신가요? 도움이 필요하신가요?”를 재생합니다. 질문 시작 5초 뒤 마이크를 약 2초 사용합니다. PCM 입력의 샘플 수, 최대 진폭, 시스템의 입력 음소거 여부만 기록합니다. 음성 파일은 저장하지 않고 카메라·네트워크·AI API를 사용하지 않습니다. 대기는 최대 5분 후 종료됩니다.

서비스 시작은 앱 화면이 보이는 상태에서 해야 합니다. Android의 마이크 권한에는 사용 중 제약이 있으며, 백그라운드에서 마이크 foreground service를 새로 만드는 것은 예외 상황을 제외하고 제한됩니다. 이미 시작한 서비스의 백그라운드 마이크 접근과 새 서비스 생성은 다른 문제입니다. [서비스 유형](https://developer.android.com/develop/background-work/services/fgs/service-types), [백그라운드 시작 제한](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

## 다른 로컬에서 만드는 앱에 붙일 부분

1. 작업자가 앱을 열었을 때 ‘음성 대기 시작’을 제공하고, 마이크·알림 권한을 확인한 뒤 Android 네이티브 서비스를 시작합니다. 이 기능은 사람을 식별하는 수동 입장 절차와 별개입니다. 기존 휴대폰 자동 식별 흐름은 유지할 수 있습니다.
2. 기존 서버의 확인 요청을 서비스에 전달합니다. 최소 입력은 `incidentId`, `workerId`, `zoneId`, `deadlineAt`입니다. 만료되거나 이미 처리한 요청은 재생하지 않습니다.
3. 서비스가 질문을 재생하고 짧은 응답 구간에만 마이크를 엽니다. 받은 음성을 AI로 분류하는 기능은 그다음 단계입니다. 이번 APK에는 AI 분류가 없습니다.
4. `receivedAt`, `promptStartedAt`, `promptFinishedAt`, `micStartedAt`, `responseCategory`, `voiceError`를 같은 사건에 기록합니다. 재생 완료와 사용자가 들었음은 서로 다른 상태입니다.
5. ‘도움 필요’ 응답은 기존 관리자 경고에 연결합니다. ‘괜찮아요’ 음성만으로 자동 해제하지 않고 기존 확인 버튼으로 확정합니다. 응답 없음·음성 오류는 기존 서버의 마감 시간을 유지합니다.
6. 서비스가 주기적으로 대기 상태를 서버에 알리도록 합니다. 서버가 일정 시간 소식을 받지 못하면 ‘음성 확인 불가’로 표시합니다. 종료된 앱은 자기 종료를 항상 전송할 수 없으므로 서버에서 만료를 판단해야 합니다.

**Android에서는 화면이 꺼져도 응답을 받으려면 네이티브 서비스가 필요합니다.** Flutter나 React Native 앱에도 해당 플랫폼 서비스 부분을 붙여야 합니다. 웹앱/PWA의 화면 밖 음성 실행을 이 APK 결과로 검증했다고 주장하면 안 됩니다.

## 실제 서버 요청을 붙일 때

이번 시험은 기기 안의 로컬 타이머입니다. ESP32 → 서버 → FCM → 휴대기기 경로와 네트워크 수신은 시험하지 않았습니다. FCM 수신 코드와 Firebase 프로젝트 설정도 포함하지 않았습니다.

고우선순위 FCM은 빠른 전달을 시도하지만 도착 시간을 보장하지 않습니다. FCM으로 일반 서비스 시작의 예외가 생기더라도 마이크 권한 제한까지 자동으로 풀리는 것으로 가정해서는 안 됩니다. 대기 서비스가 살아 있는 경우와 서비스가 없는 경우를 따로 처리합니다. 강제 종료된 Android 앱은 메시지를 다시 받으려면 사용자가 재실행해야 합니다. [FCM 우선순위](https://firebase.google.com/docs/cloud-messaging/android-message-priority), [FCM 수신 전제](https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages)

대기 서비스가 없으면 소리 있는 알림과 확인 버튼을 제시하고, 사용자가 알림을 눌러 앱을 연 뒤 음성 응답을 시작하는 흐름을 사용합니다. 앱 종료나 통신 장애가 있어도 관리자 경고 마감은 서버에서 계속 진행해야 합니다.

## 아이폰 범위

아이폰 실기기는 이번에 시험하지 않았습니다. 우선 질문을 녹음한 30초 미만 WAV/CAF/AIFF 파일을 앱에 포함하고, 푸시 알림의 사용자 지정 소리로 질문을 들려주는 방법을 검토할 수 있습니다. 알림 권한·음소거·집중 모드·전달 상태의 영향을 받습니다. 이 방법이 자동 마이크 시작이나 AI 대화를 의미하지는 않습니다. 응답은 알림을 눌러 앱을 연 뒤 받는 방식부터 구현하는 것이 적절합니다. [Apple의 사용자 지정 알림 소리](https://developer.apple.com/documentation/usernotifications/unnotificationsound?changes=_3_9)

## 아직 확인하지 않은 것

실제 AI 음성 인식과 응답 분류, 긴 작업 시간 동안의 배터리·프로세스 유지, 깊은 절전(Doze), 충전하지 않는 상태, 다른 Android 기종·버전, 블루투스·이어폰 출력, 통화 중 오디오 충돌, 방해금지 상태, 재부팅 후 동작, 원격 푸시 지연, iOS는 미검증입니다. 마이크에서 샘플이 들어왔다는 사실만으로 작업자의 말이 정확히 인식됐다고 판단하지 않습니다.

## 파일과 재시험

- APK: `build/stillwatch-voice-probe.apk` — 진단용 debug APK입니다.
- 구현: `src/com/stillwatch/voiceprobe/MainActivity.java`
- 권한·서비스 선언: `AndroidManifest.xml`
- 빌드: `build.py` — 설치된 Android SDK/JDK를 사용합니다. 경로는 환경에 맞게 변경합니다.
- 자동 시험: `test_device.py foreground|home|locked|force-stop|task-manager-stop`
- 증거: `evidence/*.jsonl`, `evidence/results.json`, `evidence/all-events.jsonl`

자동 시험은 **연결된 USB 기기의 이 검증 앱만** 제어합니다. `locked` 시험은 화면을 끄므로 잠금 해제는 사용자가 직접 해야 합니다. 결과를 비교하려면 미디어 음량과 주변 소음, 출력 장치도 함께 확인해야 합니다. 최종 시험 뒤 검증 앱은 강제 종료하여 대기를 껐고 화면을 다시 켰습니다.
